# Sanitization Report

Scope: every file in `c3-pac-artifact/` prior to the initial git commit.
Two tools used: [gitleaks](https://github.com/gitleaks/gitleaks) (credential-pattern
scanner, installed via `brew install gitleaks` for this pass) and a targeted
`grep` sweep for categories gitleaks doesn't cover (account IDs, ARNs, real
IPs, usernames in paths, email addresses, tfstate/kubeconfig presence).

## Findings and actions taken

### 1. Hardcoded real public IP address — FIXED

- **File:** `terraform/variables.tf`
- **Finding:** `cluster_endpoint_public_access_cidrs` had a default set to
  a single `/32` CIDR — the researcher's actual home/office public IP at
  the time, used during the live experiment to restrict the EKS API
  endpoint. (Value redacted from this report; the fix below removes it
  regardless of what it was.)
- **Action:** Removed the default entirely (now a required variable, same
  pattern as `alert_email`). Updated `terraform/terraform.tfvars.EXAMPLE`
  to require an explicit value with instructions (`curl -s
  https://checkip.amazonaws.com`) rather than shipping any real IP.
- **Rotation needed?** No — an IP address isn't a credential. Nothing to
  rotate; the fix is simply "don't ship it as a default."

### 2. Absolute local path (real OS username) leaked into raw results — FIXED

- **Files:** `results/phase3_admission_raw.csv` (200 occurrences),
  `results/adversarial_results.csv` (1 occurrence)
- **Finding:** The `denial_messages` column stores kubectl's raw stderr
  output verbatim for every DENIED admission check. kubectl's own error
  text embeds the full local filesystem path of the manifest file it was
  given (e.g. `error when creating "<local-path>/dataset/violations/...">`),
  which included the researcher's real macOS username — incidentally
  captured as part of a legitimate measurement (the denial reason), not
  something written intentionally. (Exact original path redacted from this
  report; see the Action below for what replaced it.)
- **Action:** Surgical string replacement of the literal local-machine path
  prefix (the absolute path to the original working directory) with the
  placeholder `<repo-root>`, across both files, via `sed`. Nothing else in
  either file was touched —
  every measured value (timings, labels, admit/deny outcome, the actual
  policy violation message) is byte-identical to the original raw data.
  This satisfies both "sanitize local paths" and "do not alter raw
  results": the path fragment is incidental metadata about *where the file
  happened to be on one machine*, not a measured result.
- **Rotation needed?** No — a local username is not a credential.

### 3. Stale TLS CA bundle in the fail-closed webhook artifact — FIXED

- **File:** `policies/gatekeeper/webhook_failclosed_scoped.json`
- **Finding:** `clientConfig.caBundle` on both webhook entries contained a
  1560-character base64 certificate chain, auto-generated by Gatekeeper's
  own cert-rotation when it was installed on the (now-destroyed) cluster.
- **Action:** Replaced both `caBundle` values with an explanatory
  placeholder string. This is **not a credential** (it's the *public* CA
  certificate a client uses to verify the webhook server, not a private
  key), but it's stale, environment-specific, and meaningless outside the
  destroyed cluster — a fresh Gatekeeper install generates its own. Shipping
  the real one would be confusing (looks load-bearing, isn't) and adds
  noise for no reproducibility benefit.
- **Rotation needed?** No.

### 4. Real corresponding-author email as a copy-paste default — FIXED

- **File:** `terraform/terraform.tfvars.EXAMPLE`
- **Finding:** The original example file had `alert_email =
  "oleksandr.p.vakhula@lpnu.ua"` (the real corresponding author's email)
  as a literal default value, not an obvious placeholder. Anyone
  reproducing the experiment who forgot to change this before running
  `terraform apply` would silently route AWS budget alert emails to the
  author's real inbox.
- **Action:** Changed to `you@example.com` with a comment explaining what
  it's for. The real email still appears appropriately in `CITATION.cff`
  as author contact metadata — that's a normal, expected place for it, not
  a leak.
- **Rotation needed?** No.

## Checked and confirmed clean (no findings)

- AWS access/secret key patterns (`AKIA...`, 40-char secrets), session tokens
- AWS account ID (12-digit) anywhere in the tree
- Full IAM ARNs referencing the real account (the only `arn:aws:` string
  present is `arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy`
  — an AWS-owned managed policy ARN, not account-specific; `:aws:` in the
  account-ID position is how AWS denotes its own managed resources)
- `*.tfstate`, `*.tfstate.backup`, `.terraform/`, `.terraform.lock.hcl`,
  real `terraform.tfvars` — none copied into the artifact at all (verified
  absent, not just gitignored)
- Kubeconfig files, cluster endpoints/hostnames, certificate data (beyond
  the caBundle above), bearer tokens
- `PRIVATE KEY` blocks
- Real hostnames / public IPs (beyond the one fixed above)
- IAM principal names tied to the real account (`c3-bootstrap`,
  `c3-experiment-claude-code`) — do not appear anywhere in the copied tree
- Email addresses beyond the corresponding author (only the intentional
  placeholder `you@example.com` remains, plus the author's own email in
  `CITATION.cff`)

## Nothing here required credential rotation

Every finding above was an **identifier** (IP, path, stale public
certificate, email) incidentally captured during a legitimate measurement
or left over from templating — not an actual AWS credential, private key,
or token. **No rotation action is needed in AWS.** This is stated
explicitly, not just implied by omission, per the task brief's instruction
to flag rotation needs prominently if applicable — none apply here.

One item worth the operator's own attention, outside this artifact's
scope: the *original* working directory (`COSE_scale_experiment/`, not
this artifact) still has `terraform.tfstate` / `terraform.tfstate.backup`
on local disk. Terraform state stores the `aws_iam_access_key.claude_code`
secret value in **plaintext** by default. That access key was already
deactivated when the cluster was destroyed (the IAM user itself was
deleted), so there is no live credential to rotate — but if you ever
re-provision with a similar config, consider enabling state encryption or
at minimum keeping `.tfstate` files out of any location that gets synced,
backed up publicly, or committed. Not a finding in this artifact (that
directory was never a candidate for copying), just a heads-up.
